# Поиск кандидатов для объявлений услуг Авито

Локальный CPU-бейзлайн для этапа кандидатогенерации. Для каждого поискового запроса решение выбирает из `benchmark_items.parquet` до 50 объявлений и сохраняет их исходные `item_id` в `answer.csv`.

Бейзлайн объединяет три источника информации: совпадение слов с учетом русской морфологии, совпадение символьных фрагментов и историю выбранных объявлений из `train.parquet`. Дополнительно учитываются локация, категория и текстовые фильтры запроса. Все вычисления выполняются на компьютере пользователя; внешние API, GPU и загрузка нейросетевых моделей не требуются.

## 1. Быстрый запуск

Нужны Python 3.12 и менеджер зависимостей `uv`. Команды ниже выполняются из корня репозитория. Версии библиотек зафиксированы в `uv.lock`, версия Python указана в `.python-version`.

Если `uv` еще не установлен:

```bash
python -m pip install uv
```

Создайте папку `data` и положите в нее исходные файлы задания:

| Путь | Содержимое |
| --- | --- |
| `data/train.parquet` | Обучающие пары «запрос — выбранное объявление» |
| `data/benchmark_items.parquet` | Корпус объявлений, из которого разрешено выбирать кандидатов |
| `data/benchmark_queries.parquet` | Запросы, для которых нужно подготовить ответ |

Установите зависимости и запустите решение:

```bash
uv sync --frozen
uv run --frozen python main.py run
```

`uv sync --frozen` создает окружение `.venv` и устанавливает версии из `uv.lock`. При первой установке нужны доступ к пакетам и установленный Python 3.12. Для работы в изолированной среде подготовьте интерпретатор и окружение заранее.

Команда `run` читает данные, строит индексы, собирает историю взаимодействий, обрабатывает все запросы и записывает `answer.csv` в корень проекта. Предварительно обучать отдельную модель или запускать дополнительные скрипты не нужно.

После подготовки окружения можно явно запретить сетевые обращения менеджеру зависимостей:

```bash
uv run --offline --frozen python main.py run
```

Сами Python-скрипты обращаются только к локальным файлам.

## 2. Что решает бейзлайн

В поисковом каскаде кандидатогенерация выбирает небольшое множество объявлений из большого корпуса. Следующий этап ранжирования сможет работать только с этим множеством. Поэтому здесь важна полнота: подходящие пользователю объявления должны попасть в итоговые 50 кандидатов.

Каждая строка `train.parquet` описывает положительное взаимодействие: пользователь ввел запрос с определенными признаками и выбрал объявление. Разметки отрицательных взаимодействий в этих данных нет. Бейзлайн использует положительные пары для построения истории и оценки популярности, а текстовые индексы строит по всему доступному корпусу объявлений.

По условиям задания размеры данных следующие:

| Файл | Число строк | Единица наблюдения |
| --- | ---: | --- |
| `train.parquet` | 497 673 | Одна пара «запрос — выбранное объявление» |
| `benchmark_items.parquet` | 189 212 | Одно объявление |
| `benchmark_queries.parquet` | 2 452 | Один запрос |

Эти числа описывают набор из задания. Они не зашиты в код: программа обрабатывает фактическое число строк в файлах.

## 4. Какие признаки используются

### Признаки запроса

| Поле | Как используется |
| --- | --- |
| `query_id` | Переносится в ответ без изменения. В вычислении релевантности не участвует |
| `search_query` | Основной текст для BM25 и символьного поиска; часть ключа истории |
| `search_location_id` | Задает локальную выдачу, участвует в истории и резервном заполнении |
| `search_is_delivery_search` | Участвует в точном ключе истории |
| `search_infm_params_text` | Добавляется к запросу в отдельном BM25-канале; участвует в точном ключе истории |
| `search_category` | Участвует в точном ключе истории и мягкой корректировке итоговой оценки |

Флаг доставки не включает отдельный поиск по расстоянию и не исключает объявления из других локаций. В этой реализации он различает контексты запросов в истории.

Текстовые фильтры не преобразуются в жесткие условия. Например, фраза «Рейтинг пользователя 4 звезды и выше» добавляется к тексту запроса, но не становится числовой проверкой `item_rating >= 4`. Это особенность текущего бейзлайна.

### Признаки объявления

| Поле | Как используется |
| --- | --- |
| `item_id` | Идентификатор кандидата и связь объявления с историей |
| `item_title_raw` | Входит в оба текстовых индекса; в BM25 повторяется несколько раз |
| `item_description_raw` | Первые 250 слов входят в BM25 |
| `item_infm_params_text` | Первые 100 слов входят в оба текстовых индекса |
| `item_location_id` | Позволяет выбирать объявления из локации запроса |
| `item_category_id` | Используется для корректировки оценки при несовпадении категории |
| `item_rating_reviews_count` | Дополнительный критерий в резервной выдаче |
| `item_rating` | Следующий критерий в резервной выдаче |
| `item_microcat_id` | Не используется |
| `item_price` | Не используется |
| `item_latitude`, `item_longitude` | Не используются; расстояние между точками не рассчитывается |
| `item_is_phone_hidden`, `item_is_message_forbidden` | Не используются |

Рейтинг и количество отзывов не входят в основную формулу релевантности. Они помогают упорядочить резервные объявления, если основные каналы дали меньше 50 уникальных кандидатов.

В `train.parquet` программа читает только пять полей `search_*` и `item_id`. Признаки объявления из train для итогового поиска не нужны: тексты и метаданные берутся из `benchmark_items.parquet`. Пары с `item_id`, отсутствующими в benchmark-корпусе, не включаются в историю. Поэтому история не может добавить в ответ объявление за пределами разрешенного корпуса.

## 5. Общий порядок работы

Полный запуск состоит из следующих шагов:

1. Прочитать конфигурацию и проверить исходные идентификаторы.
2. Подготовить весь корпус `benchmark_items`: обрезать длинные текстовые поля и сохранить необходимые данные локально.
3. Построить BM25-индекс по словам с лемматизацией.
4. Построить символьный TF-IDF-индекс по заголовкам и параметрам.
5. Подготовить историю положительных взаимодействий из train.
6. Для каждого запроса получить несколько списков кандидатов.
7. Объединить списки с помощью взвешенного Reciprocal Rank Fusion.
8. Скорректировать оценки с учетом категории, выбрать первые 50 уникальных объявлений и при необходимости дополнить список.
9. Сохранить `answer.csv` и проверить его соответствие формату задания.

Текстовые индексы строятся по всему benchmark-корпусу, включая объявления, которых нет в train. Для их нахождения не требуется наличие истории: достаточно текстового совпадения с запросом.

## 6. Подготовка текстов

### Два представления объявления

Для BM25 документ составляется в следующем порядке:

```text
заголовок + заголовок + заголовок + параметры + описание
```

По умолчанию заголовок повторяется три раза, параметры ограничиваются первыми 100 словами, описание — первыми 250 словами. Сам заголовок по числу слов не обрезается.

Повторение заголовка увеличивает частоту его слов в документе. Это дает словам из заголовка дополнительный вес, поскольку обычно именно в нем кратко названа услуга. Эффект не равен простому умножению итоговой оценки на три: BM25 учитывает насыщение частоты и длину документа.

Для символьного поиска документ короче:

```text
заголовок + параметры
```

Заголовок включается один раз, параметры также ограничиваются 100 словами. Описание в этот индекс не входит. Символьный канал сосредоточен на кратком названии и характеристиках услуги.

Обрезание параметров и описания выполняется по последовательностям непробельных символов до дальнейшей токенизации. Лимиты задаются в секции `text` конфигурации.

### Нормализация для BM25

Текст переводится в нижний регистр. Регулярное выражение выделяет последовательности русских букв, латинских букв и цифр. Знаки пунктуации не становятся отдельными токенами.

Затем каждое слово передается в `pymorphy3`: берется начальная форма первого варианта морфологического разбора. Так формы вроде «телевизоров» и «телевизор» могут совпасть в индексе.

Результаты разбора кешируются: одно и то же слово не нужно повторно разбирать для каждого объявления. Размер кеша — до 200 000 токенов. Стоп-слова специально не удаляются, отдельный словарь синонимов не применяется.

### Нормализация для символьного поиска и истории

Здесь используется отдельная процедура: нижний регистр, замена `ё` на `е`, выделение буквенно-цифровых фрагментов и соединение их одним пробелом. Лемматизация к ключам истории и символьным n-граммам не применяется.

Это означает, что различия в регистре и пунктуации не разделяют одинаковые запросы в истории, а разные словоформы все еще могут образовывать разные ключи. Их сходство учитывают текстовые каналы.

Пропуски в текстовых полях превращаются в пустую строку. Категориальные признаки переводятся в строковое представление; например, числовые `1` и `1.0` получают одинаковый ключ. Для отсутствующего категориального значения используется внутренний маркер пропуска.

Нормализация не применяется к `query_id` и `item_id`. Они сохраняются в исходном виде, включая регистр `query_id` и ведущие нули.

## 7. Поиск по словам: BM25

BM25 оценивает, насколько слова запроса характерны для конкретного объявления. Слова, встречающиеся во многих объявлениях, обычно дают меньший вклад, чем более редкие. Частое повторение слова внутри одного документа увеличивает оценку с насыщением, а длина документа учитывается отдельно.

В реализации используются `k1 = 1.5` и `b = 0.75`. Для слова $t$ обратная документная частота равна:

$$
\mathrm{IDF}(t)=\ln\left(1+\frac{N-\mathrm{df}(t)+0.5}{\mathrm{df}(t)+0.5}\right),
$$

где $N$ — число объявлений в корпусе, а $\mathrm{df}(t)$ — число объявлений, содержащих слово.

Итоговая оценка документа $d$ для запроса $q$:

$$
s_{\mathrm{BM25}}(q,d)=\sum_{t\in\mathrm{unique}(q)}
\mathrm{tf}(t,q)\,\mathrm{IDF}(t)
\frac{\mathrm{tf}(t,d)}
{\mathrm{tf}(t,d)+k_1\left(1-b+b\frac{|d|}{\mathrm{avgdl}}\right)}.
$$

Здесь `tf` — число вхождений слова после токенизации, $|d|$ — длина подготовленного документа в токенах, `avgdl` — средняя длина по всему корпусу. Повторение заголовка уже включено в `tf` и длину документа.

Используется вариант нормировки, соответствующий `bm25s(method='lucene')`. В распространенной записи BM25 в числителе также стоит множитель $k_1+1$. Здесь он опущен; при фиксированном `k1` это общий множитель и на порядок объявлений внутри BM25-выдачи не влияет.

Документ, в котором после токенизации не осталось слов, получает служебный токен, чтобы длина была определена. Эта деталь не формирует готовых ответов и не зависит от идентификаторов запросов.

### Глобальная и локальная выдачи

По BM25 формируются два списка:

| Выдача | Где ищем | Лимит по умолчанию |
| --- | --- | ---: |
| Глобальная | Во всем benchmark-корпусе | 250 |
| Локальная | Среди объявлений с `item_location_id`, совпадающим с `search_location_id` | 150 |

Локальный список строится из оценок всех объявлений нужной локации. Он не получается обрезанием уже выбранного глобального топа. Поэтому локально подходящее объявление может попасть в объединение даже тогда, когда не вошло в глобальные 250.

При неизвестной локации или отсутствии объявлений в ней локальная выдача не добавляется. Глобальная выдача сохраняется. Равенство локаций проверяется по идентификаторам; близость соседних локаций не вычисляется.

## 8. Символьный TF-IDF

Символьный канал ищет совпадения в коротких фрагментах слов. Он дополняет BM25, когда тексты содержат разные окончания, некоторые опечатки или близкие варианты написания. Это сходство написания: понимание произвольных синонимов из него не следует.

Используется анализатор `char_wb` из scikit-learn с длинами n-грамм от 3 до 5 символов. Фрагменты выделяются внутри слов с учетом пробелов на их границах. Например, в слове «ремонт» встречаются фрагменты «рем», «емо», «мон», «онт»; дополнительно анализатор учитывает более длинные фрагменты и границы слова.

Каждому фрагменту присваивается TF-IDF-вес:

$$
\mathrm{idf}_{\mathrm{char}}(g)=\ln\frac{N+1}{\mathrm{df}(g)+1}+1,
\qquad
v_d(g)=\mathrm{tf}(g,d)\cdot\mathrm{idf}_{\mathrm{char}}(g).
$$

Вектор документа нормируется по L2-норме. Запрос обрабатывается тем же анализатором и с теми же IDF, после чего также нормируется. Сходство — скалярное произведение нормированных векторов, то есть косинусная близость. Если у запроса нет известных индексу фрагментов, его оценки равны нулю.

Словарь ограничен 200 000 признаков. Если фрагментов больше, выбираются наиболее частые по суммарному числу вхождений во всем корпусе. IDF, выбор признаков и нормировка считаются согласованно для всего индекса.

Символьный канал возвращает до 100 объявлений глобально и до 150 внутри локации. Для локальной выдачи используется тот же параметр `local_k`, что и у BM25.

## 9. Учет текстовых фильтров

Если у запроса есть и непустой `search_query`, и непустой `search_infm_params_text`, запускается дополнительный BM25-поиск по строке:

```text
текст запроса + текст фильтров
```

Из него берутся до 250 кандидатов глобально. Отдельного локального списка для расширенного запроса нет. Основной BM25 и символьный поиск при этом продолжают работать с обычным текстом запроса.

Вес расширенного канала равен `0.3`. Он дает дополнительный сигнал от фильтров, сохраняя больший вклад собственно поискового текста.

Если текст запроса пуст, но фильтры заполнены, фильтры используются как основная строка для BM25 и символьного поиска. Дополнительный расширенный канал в этом случае не нужен. Если пусты оба поля, текстовые совпадения отсутствуют и применяется резервная выдача.

## 10. История взаимодействий из train

История добавляет объявления, которые уже выбирали пользователи по совпадающим нормализованным запросам. Она строится автоматически из `train.parquet` и не использует `query_id` бенчмарка.

Полный ключ контекста состоит из пяти полей в следующем порядке:

```text
текст запроса, локация, доставка, текст фильтров, категория
```

Сначала остаются только объявления из benchmark-корпуса. Затем удаляются полные дубли пары «контекст — item_id». Повтор одной и той же пары не увеличивает ее вес. При этом один `item_id`, выбранный в нескольких разных контекстах, остается представленным в каждом из них.

Для текущего запроса строятся три списка:

| Канал | Что должно совпасть | Лимит | Вес |
| --- | --- | ---: | ---: |
| `history_context` | Все пять полей полного ключа | 100 | 1.5 |
| `history_text_location` | Текст запроса и локация | 100 | 1.0 |
| `history_text` | Только текст запроса | 100 | 0.5 |

Чем точнее совпадение условий, тем выше вес канала. Более широкие списки помогают, когда запрос встречался в train с другими фильтрами или в другой локации.

Внутри каждого списка объявления сортируются по числу уникальных взаимодействий после дедупликации. Для точного контекста у каждого объявления остается максимум одна такая пара. Для более широких списков одно объявление может встречаться в нескольких контекстах и получить больший счетчик.

При равенстве счетчиков сначала выбирается объявление с большей общей популярностью в подготовленной истории, затем — с лексикографически меньшим `item_id`. Под популярностью здесь понимается число уникальных пар «полный контекст — это объявление», а не исходное число строк до удаления дублей.

Если нормализованный текст запроса не встречался в train, исторические списки пусты. Если сам текст запроса пуст, каналы истории не используются даже при наличии фильтров. В обоих случаях решение продолжает работать за счет остальных источников.

## 11. Объединение результатов: взвешенный RRF

Численные оценки BM25, символьного TF-IDF и истории имеют разный смысл и масштаб. Поэтому итоговая оценка строится по месту объявления в выдачах каждого канала.

Для объявления $d$ используется взвешенный Reciprocal Rank Fusion:

$$
\mathrm{RRF}(d)=\sum_{c:\,d\in L_c}\frac{w_c}{K+\mathrm{rank}_c(d)},
\qquad K=60.
$$

$L_c$ — список кандидатов канала, $w_c$ — его вес. Ранги начинаются с 1. Если объявления нет в конкретном списке, вклад этого канала равен нулю. Внутри одного списка повторный `item_id` не учитывается, а попадание в разные каналы суммирует вклады.

Полный набор каналов и параметры по умолчанию:

| Канал | Ключ веса | Максимум кандидатов | Вес |
| --- | --- | ---: | ---: |
| BM25 по всему корпусу | `bm25` | 250 | 1.0 |
| BM25 внутри локации | `bm25_local` | 150 | 1.0 |
| Символьный TF-IDF по всему корпусу | `char` | 100 | 0.6 |
| Символьный TF-IDF внутри локации | `char_local` | 150 | 0.6 |
| BM25 по запросу с фильтрами | `query_with_filters` | 250 | 0.3 |
| История полного контекста | `history_context` | 100 | 1.5 |
| История текста и локации | `history_text_location` | 100 | 1.0 |
| История текста | `history_text` | 100 | 0.5 |

Каждый список может быть короче лимита: текстовые каналы включают только объявления с положительной конечной оценкой, а история — только найденные взаимодействия. При всех активных каналах суммарный верхний предел до удаления пересечений равен 1 200 кандидатам. Фактическое число уникальных объявлений обычно меньше.

Например, для объявления на первом месте глобального BM25 и втором месте символьной выдачи вклад этих двух каналов составит:

$$
\frac{1.0}{60+1}+\frac{0.6}{60+2}\approx 0.02607.
$$

Если это же объявление встретится в истории или локальном поиске, соответствующие вклады добавятся. Значение RRF служит для выбора кандидатов и не является вероятностью клика.

## 12. Корректировка по категории

После RRF применяется мягкая корректировка. Если категория запроса задана и отличается от `item_category_id`, оценка объявления умножается на `0.85`.

Объявление при этом остается среди кандидатов. Такой подход уменьшает его приоритет, сохраняя возможность найти релевантную услугу, размещенную в другой категории.

Значение категории запроса `0` и пропуск трактуются как отсутствие заданной категории: штраф не применяется. Если категория запроса задана, а категория объявления отсутствует, они считаются несовпадающими.

Корректировка выполняется до выбора финальных 50. При равных итоговых оценках порядок определяется по `item_id`.

## 13. Выбор 50 кандидатов и резервная выдача

Из объединенного списка после корректировки берутся первые 50 уникальных объявлений. Если найдено меньше, свободные места заполняются резервными кандидатами из того же benchmark-корпуса.

Резервный порядок задается последовательно:

1. Большее число уникальных взаимодействий в истории train.
2. Большее количество отзывов.
3. Более высокий рейтинг.
4. Лексикографически меньший `item_id`.

Если включен локальный поиск, сначала перебираются резервные объявления из локации запроса, затем общий резервный список. Уже выбранные ID пропускаются. При отсутствии известной локации используется общий список.

Недостающие рейтинг и количество отзывов заменяются нулями. Если история отключена, популярность для резервного порядка также равна нулю, и выбор определяется остальными критериями.

Резервные объявления добавляются после основного поиска; дополнительная RRF-оценка или штраф по категории для них не рассчитываются. Они помогают использовать доступный лимит кандидатов, но не гарантируют релевантность при отсутствии текстовых и исторических совпадений.

Для непустого корпуса программа возвращает `min(50, число объявлений)` уникальных ID. На корпусе из задания это 50 ID для каждого запроса. Ограничение «до 50» также соблюдается на меньшем корпусе.

## 14. Формат answer.csv

Выходной файл записывается в UTF-8 с разделителем «запятая» и содержит ровно две колонки в указанном порядке:

| Колонка | Содержимое |
| --- | --- |
| `query_id` | Исходный строковый ID запроса длиной 16 символов |
| `answer` | До 50 исходных `item_id`, разделенных одним пробелом |

Файл создается через `pandas.DataFrame.to_csv(..., index=False, encoding='utf-8')`. Индекс DataFrame не сохраняется. Запросы выводятся в том же порядке, в котором они прочитаны из `benchmark_queries.parquet`.

До записи и после повторного чтения CSV проверяется, что:

- колонки называются ровно `query_id` и `answer`;
- каждый исходный `query_id` присутствует один раз, без лишних запросов;
- ID запроса остается строкой длиной 16 символов;
- в одной строке не больше 50 кандидатов и нет повторов;
- каждый `item_id` состоит из 16 символов `0-9a-f`;
- каждый кандидат существует в `benchmark_items.parquet`.

При повторном чтении используется `dtype=str`, поэтому ведущие нули не теряются. Значение `query_id` не переводится в нижний регистр.

## 15. Команды запуска

### Полный цикл

```bash
uv run --frozen python main.py run
```

Перестраивает индексы по текущим данным, сохраняет их в `artifacts/`, получает кандидатов и перезаписывает файл по `paths.answer`.

### Повторный поиск по готовым индексам

```bash
uv run --frozen python main.py predict
```

Загружает сохраненные индексы и заново формирует ответ для текущего файла запросов. Это удобно, если изменился только набор запросов.

Перед загрузкой сравниваются контрольные суммы `train.parquet`, `benchmark_items.parquet`, четырех рабочих модулей и параметры секций `text`, `search`, `memory`. Если они изменились, программа просит заново выполнить `run`.

Поэтому при `predict` исходные train и benchmark-корпус должны оставаться доступными: они нужны для проверки соответствия индекса. Сам train повторно не преобразуется в таблицу взаимодействий. Новый файл запросов не требует перестроения индекса, если данные корпуса, train, код и перечисленные параметры прежние.

### Проверка готового файла ответа

```bash
uv run --frozen python main.py check
```

Проверяет соответствие CSV исходному списку запросов и корпусу объявлений. Эта команда не строит индексы и не измеряет Recall@50. Для нее нужны файл ответов, `benchmark_queries.parquet` и `benchmark_items.parquet`.

### Другой файл конфигурации

```bash
uv run --frozen python main.py run --config config.yaml
```

Параметр `--config` доступен для всех трех команд. Относительные пути внутри YAML считаются от папки самого YAML-файла. Можно использовать абсолютные пути. Для Windows в YAML удобно писать путь с прямыми слешами, например `C:/datasets/avito/train.parquet`.

### Пути

| Параметр | По умолчанию | Назначение |
| --- | --- | --- |

| `paths.answer` | `answer.csv` | Итоговый CSV |

### Текст и поиск

| Параметр | Значение | Назначение |
| --- | ---: | --- |
| `text.title_repeat` | 3 | Число повторений заголовка в BM25-документе |
| `text.params_words` | 100 | Число слов параметров объявления для обоих индексов |
| `text.description_words` | 250 | Число слов описания для BM25 |
| `search.use_char` | `true` | Включить символьный TF-IDF |
| `search.use_history` | `true` | Включить историю и популярность по train |
| `search.use_local` | `true` | Добавлять локальные текстовые выдачи и локальный резерв |
| `search.global_k` | 250 | Лимит глобального BM25 и отдельного BM25 по запросу с фильтрами |
| `search.local_k` | 150 | Лимит каждой локальной текстовой выдачи |
| `search.char_k` | 100 | Лимит глобальной символьной выдачи |
| `search.history_k` | 100 | Лимит каждого из трех исторических списков |
| `search.char_max_features` | 200 000 | Максимальное число символьных признаков |
| `search.rrf_k` | 60 | Константа сглаживания позиции в RRF |

Веса отдельных каналов находятся в `search.weights` и перечислены в разделе об RRF. Важно различать `rrf_k` и размеры выдач: `rrf_k` не задает число кандидатов, а влияет на относительный вклад позиций.

`use_local: false` отключает локальные текстовые списки и локальный приоритет резерва. Исторические каналы по локации при включенном `use_history` сохраняются: это самостоятельный источник информации.

Итоговый лимит 50 определяется заданием и не меняется при увеличении размеров промежуточных списков. Увеличение `global_k` или `history_k` расширяет только множество, из которого выбираются эти 50.

### Обработка данных порциями

| Параметр | Значение | Что ограничивает |
| --- | ---: | --- |
| `memory.parquet_batch_rows` | 256 | Число объявлений в одной порции чтения исходных текстов |
| `memory.index_shard_rows` | 1 024 | Число объявлений в одном блоке текстового индекса |
| `memory.query_batch_rows` | 8 | Число запросов, для которых одновременно считаются текстовые оценки |

Значения должны быть положительными. Они регулируют размеры промежуточных данных, сохраняя поиск по всему корпусу. Статистики слов и символьных признаков не вычисляются независимо внутри маленьких блоков.

## 17. Как хранятся индексы

Корпус объявлений читается из Parquet порциями. После обрезания параметров и описаний нужные поля записываются в локальную SQLite-базу. Она создается автоматически; отдельный сервер базы данных не нужен.

Текстовые индексы строятся в два прохода. Сначала для каждого блока сохраняются частоты признаков и собираются статистики по всему корпусу. Затем частоты преобразуются в BM25 или TF-IDF-веса с использованием общих статистик. Так средняя длина документа, IDF и выбор символьных признаков согласованы между блоками.

Разреженные данные хранят только ненулевые значения. При поиске читаются списки объявлений для признаков, присутствующих в запросе. Для небольшой порции запросов создается матрица оценок по всему корпусу; общая плотная матрица для всех запросов одновременно не строится.

После `run` папка `artifacts/` содержит:

| Путь | Содержимое |
| --- | --- |
| `corpus.sqlite` | Подготовленные тексты и метаданные объявлений |
| `index_data/bm25/` | Блоки BM25-индекса |
| `index_data/char/` | Блоки символьного индекса, если канал включен |
| `index_data/history.parquet` | История после удаления дублей, если канал включен |
| `index.pkl` | Сохраненная модель: словари, метаданные и ссылки на индексы |
| `manifest.json` | Сигнатура данных, кода и параметров для команды `predict` |

Один `index.pkl` не содержит весь текстовый индекс. При переносе готового результата сохраняйте всю папку `artifacts/`. Загружайте `index.pkl`, созданный собственным запуском проекта: формат pickle предназначен для доверенных локальных объектов.

Папку `artifacts/` можно восстановить командой `run`. Одновременные запуски должны использовать разные папки артефактов, поскольку построение заменяет файлы индекса.

Бейзлайн работает на CPU. Время и объем ресурсов зависят от длины текстов, размера словаря, числа запросов и скорости диска. Для хранения индексов требуется свободное место. В репозитории не задается универсальная гарантия по времени или потреблению памяти на любой машине.

## 18. Метрика и интерпретация результата

Целевая метрика — средний Recall@50 по запросам:

$$
\mathrm{Recall@50}=\frac{1}{|Q|}\sum_{q\in Q}
\frac{|C_{50}(q)\cap R(q)|}{|R(q)|},
$$

где $C_{50}(q)$ — возвращенные кандидаты, $R(q)$ — все релевантные объявления для запроса, а $Q$ — множество оцениваемых запросов.

Каждый запрос имеет одинаковый вес в среднем. Если у одного запроса два релевантных объявления и найдено одно, вклад этого запроса равен `0.5`. Порядок кандидатов внутри уже выбранного набора на метрику не влияет. При этом порядок промежуточной выдачи важен: именно по нему из общего множества выбираются финальные 50.

В `benchmark_queries.parquet` нет целевой разметки. Команды `run` и `predict` создают предсказания, а `check` проверяет формат; ни одна из них не сообщает качество на скрытых ответах. Числовое значение Recall@50 на реальном бенчмарке в этом описании не заявляется.

## 19. Особенности и границы подхода

Сочетание каналов позволяет использовать разные сигналы. BM25 учитывает слова и словоформы; символьный поиск — близость написания; история — ранее выбранные объявления; локальные списки — совпадение локации. Совместное попадание объявления в несколько списков увеличивает его итоговый приоритет.

При этом решение остается лексическим бейзлайном. Оно не строит семантические эмбеддинги и может пропускать услуги, описанные совершенно другими словами. История помогает прежде всего для повторяющихся нормализованных текстов. Цена, расстояние и доступность способов связи не участвуют в отборе.

Веса каналов, лимиты и штраф за категорию — фиксированные настройки данного бейзлайна. Они не обучаются автоматически и не представлены как оптимальные для скрытого бенчмарка. В коде нет подстановки готовых ответов по `query_id`; все кандидаты вычисляются из предоставленных данных.
